SECURITY

HOW STUBS WORKSAND WHERE IT STOPS

What Stubs does with your .env values, what the server keeps, and what it doesn't protect against. Everything here describes code that runs on stubs.talix.app or in the @talix/stubs CLI.

Encryption happens on your machine

The browser, or the CLI, does all of the cryptography. The server never receives anything that could decrypt a stub.

  • It draws a random 256-bit key with crypto.getRandomValues and puts it in the link after the #: /t#v1.<key>. Browsers don't send the part after # to any server, and the CLI never sends it either.
  • HKDF-SHA256 turns that key into three values: a 128-bit storage id, an AES-GCM-256 key, and a 256-bit claim secret.
  • The .env text is encrypted with AES-GCM under a fresh random IV. The storage id is bound in as associated data, so ciphertext can't be moved to another id.
  • The server receives the id, a SHA-256 hash of the claim secret, the ciphertext, the IV, and how long to keep it.

To check or open a stub, the client sends the claim secret. The server hashes it and compares it with the stored hash in constant time. Only the link can produce the claim secret, so the id on its own (it appears in request logs) can't check, open, or burn a stub. A wrong secret gets the same answer as a stub that doesn't exist, and changes nothing.

A stub opens once. The server checks the secret, deletes the ciphertext, and returns it in one step that holds a lock on that stub's storage, so two people opening it at the same moment can't both get it. The client then decrypts it locally. If the ciphertext was altered, decryption fails and the stub is reported as tampered. It's void by then.

On the web page, loading a link only checks its status. Revealing takes a click, so chat link previews can't burn a stub. The page takes the key out of the address bar as soon as it loads. The API refuses cross-site requests, so another website can't make your browser burn one.

What the server stores

Each stub lives in its own Cloudflare Durable Object, named by the storage id. It holds:

  • the SHA-256 hash of the claim secret
  • the ciphertext (at most 32 KB of .env text before encryption) and its IV
  • the lifetime the sender picked, and the expiry time

The sender picks how long a stub stays valid: 5 minutes, 1 hour (the default), 1 day, or 7 days. An alarm deletes everything at expiry.

When a stub is opened, everything but the expiry time is deleted at once. The expiry time stays so the id can't be reused before then, and the alarm removes that too.

SQLite-backed Durable Objects keep 30 days of point-in-time recovery. In that window, whoever controls the Cloudflare account could restore deleted ciphertext. It's useless without the key, which never reached the server.

The Worker doesn't log ids, keys, claim secrets, or ciphertext. When something fails, it logs the error's type, or the HTTP status if forwarding analytics fails, and nothing else. Cloudflare still sees each request's IP address and path, and the path of a check or open includes the storage id. The Worker uses the IP only as a rate-limit key: 30 creates and 120 checks or opens per client per minute, per Cloudflare location. IPv6 clients are counted per /64.

Locking a stub to one machine

An ordinary link works for anyone who has it. A locked link opens on one machine only.

  • The recipient runs npx -y -- @talix/stubs@{{STUBS_CLI_VERSION}} init once. It creates an X25519 key pair in ~/.config/stubs/identity, or under $XDG_CONFIG_HOME/stubs/ if that's set (file mode 0600, folder 0700), and prints a public id that starts with stubs1.
  • The sender pastes that id into "Lock to a recipient" on the site, or runs stubs push --to <id>.
  • The link then carries the stub's key wrapped to that public key: an ephemeral X25519 key exchange, HKDF-SHA256, then AES-GCM. Only stubs pull on the machine holding the private key can unwrap it.

This protects against the link leaking. A locked link can sit in a chat, an issue, an agent's transcript, or browser history, and whoever copies it still can't open, check, or burn the stub. The server stores a locked stub exactly like an unlocked one and can't tell them apart.

It doesn't protect against someone who can read the identity file. Like an SSH key, it relies on file permissions and has no passphrase. Browsers can't open locked stubs; only the CLI can.

Keeping values away from agents

The CLI and its MCP server let an agent move a stub into a project without the values entering its context.

  • stubs pull <link> writes the values into .env.local (or --to <file>) and prints only the key names. No flag prints a value, and no error message includes one. The values go to a temp file that's renamed into place, with mode 0600 (or the existing file's mode, if that's stricter). If that write fails after the stub is opened, the values are saved to a 0600 file under the stubs config folder instead, and the error names that file.
  • Pull and check output, every error, and every MCP tool result go through one redaction step (cli/src/redact.ts). It blanks URLs, link fragments, base64url runs of 43 or more characters, and public ids, so a link passed where a path was expected can't come back in an error. A few commands skip it for the thing they exist to print: push prints the new link (and the id it's locked to), init and id print this machine's public id, and skill show prints the skill. None of them prints a value.
  • The git guard runs before the stub is opened. If git would track the target file, pull exits 5 and says what to add to .gitignore. If git can't answer inside what looks like a repository, it refuses rather than guess.
  • stubs pull - reads the link from stdin, which keeps it out of the process list and shell history.
  • The MCP server has pull_stub and check_stub and no push tool. pull_stub refuses absolute paths and .., so the path it's given has to stay inside the project. That's a check on the path as written. A symlink you put in the project is followed, even if it points outside, and the git guard then checks the file it points to.
  • Every command the site and docs show pins an exact CLI version, so npx never picks up a newer release on its own.

The CLI can't stop an agent from reading the file afterwards. The agent skill and the suggested AGENTS.md line tell agents never to read or print .env* files.

Threat model

Stubs is built so that:

  • the server, and anyone who reads its storage or logs, can't learn the values
  • someone who knows a stub's id but not its link can't check, open, or burn it
  • link previews and unfurlers can't burn a stub
  • two people can't both open the same stub
  • links can't be guessed: each carries a fresh 256-bit key, and every guess goes through the rate-limited server
  • altered ciphertext fails to decrypt instead of producing wrong values
  • a locked link is useless to anyone but the recipient's machine

What it doesn't protect against

  • A dropped response. Opening is single-phase: the server deletes the stub before its answer reaches you. If the connection drops at that moment, the stub is gone and nobody has the values. The CLI exits 7 ("uncertain") and tells you to run the same command again, which either pulls the values or reports the stub as void. If it's void, ask the sender for a new link. A grace window would fix this but weaken the one-time guarantee.
  • A leaked unlocked link. Until it's opened, an unlocked link is a bearer token: anyone who has it can open it first, wherever it was sent and in the recipient's browser history. Lock the stub to the recipient's machine to close this.
  • Tools that print their environment. A tool that prints its environment on error can leak a value into an agent's transcript. Run it as npx -y -- @talix/stubs@{{STUBS_CLI_VERSION}} run -- <command> and stubs swaps each value for [stubs:KEY] in its output, including common base64, URL and JSON forms. That stops accidents, not an agent that's trying: a script can still open the file, write to the terminal device directly, or print a value in an encoding stubs doesn't know.
  • An agent that reads the file on purpose. An agent runs as you, so it can read anything you can, including .env.local. skill install --protect adds Claude Code deny rules for .env* files, but those don't cover files a script opens. Keeping values where an agent can't read them is planned, not built.
  • A compromised machine on either end. Malware, or a browser extension that can read the page, sees the values when they're decrypted.
  • Changed site code. The web page runs whatever JavaScript stubs.talix.app serves. If that code were changed, it could read the key. The CLI runs a pinned version from npm instead.
  • Session restore. Until an unlocked stub is opened, its link is kept in the tab's session storage so a refresh works. Browsers can write session storage to disk. It's removed once the stub is opened or found void.
  • An untrusted project. npx prefers a matching package already in the project's node_modules. In a checkout you don't trust, install the CLI globally and run stubs from your PATH.
  • Metadata. The server knows when a stub was created and opened, when it expires, and the ciphertext's length, which tracks the .env's length. Anyone with an id can tell whether a stub under it exists and hasn't expired, because creating another one with that id is refused.

Analytics

Stubs counts usage without recording anything that identifies a stub or what's in it. There are no cookies and no session replay.

  • The browser sends one kind of event to this site's own /api/events: a page view for / or /t, with the path only. It never sends the link, the key, or anything typed or pasted.
  • On /, the page view also carries the referring site's domain (never its path) and, if the link had them, utm_source, utm_medium, and utm_campaign. No other part of the address is sent, and /t never sends any of it.
  • The Worker checks each event against a fixed allowlist, rebuilds it, and forwards it to PostHog. Each page load gets a random id that's kept in memory only, and PostHog uses it as the session id. PostHog is told not to build person profiles or look up location.
  • The browser sends nothing if Global Privacy Control or Do Not Track is on.
  • The Worker counts stub creates (with the lifetime picked) and claims (opened or found nothing) in Cloudflare Workers Analytics Engine, by client: web, cli, or mcp. The CLI and MCP server send no events of their own. They only name themselves in an X-Stubs-Client header. Creates and claims sent with Global Privacy Control or Do Not Track aren't counted.
  • It also counts Worker errors (route and error type) and rate-limited requests (route), even with Global Privacy Control or Do Not Track on, since they say nothing about who sent them.
  • None of these counts carries an id, link, key, claim secret, ciphertext, size, IP, or user agent.
  • This page runs no JavaScript and sends nothing.

Reporting a vulnerability

Email security@talix.app. Say what you found, how to reproduce it, and what an attacker could do with it. Test only with stubs you created yourself, and please don't publish details before a fix is out. The same contact is in /.well-known/security.txt.
